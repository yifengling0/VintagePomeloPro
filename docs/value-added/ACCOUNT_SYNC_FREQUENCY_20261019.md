# 2026-10-19 账号同步降频与定时器复核

客户端降频已实现，后端摘要及错误已接入 AGC invocation logger。定时器自动调度验收未通过，每日 16:05 的表达式仍被平台拒绝，业务任务保持停用。本文中的时间均为北京时间。

## 客户端行为

- 启动时等待账号恢复和初始化完成，账号事件及会员恢复事件合并成一轮同步；登录、账号切换仍触发同步。
- 本地变化按 2 秒合并；传输中的变化排入后续一轮。普通切回前台只继续待完成任务，不增加空闲检查。其他设备变化在下次启动或手动同步时获取。
- 删除会员详情每 30 秒的云端检查。前台检查只读取本地通知权限与系统 token；仅账号、安装标识、token、权限变化或明确强制操作才登记/撤销。登记请求合并，成功撤销只执行一次，token 在登记期间再次变化时追加一轮。
- 能力查询成功结果缓存 5 分钟，并发查询合并；手动刷新、购买和恢复购买强制重新读取能力。会员查询保持并发合并，不把能力缓存用于授权；购买、恢复购买、管理订阅返回后仍核验权益。
- 配置同步及通知登记/撤销的暂时失败按 1、5、15 分钟重试，最多三次，仅在前台执行。切后台保存截止时间；三次后等待新变化、下次启动或明确重试。账号隔离、待同步数据及 CAS 冲突保护保留。
- 购买流程复用已经成功的提醒预检，避免 UI 和服务层连续登记同一设备。

## 定时器实验

执行前保存了完整版本、触发器、环境配置以及 `$latest` 的原始 ZIP。备份含凭据，保存在工作区私有目录，不纳入版本控制。

实际初始状态：`renewal` 绑定 `$latest`，`@every 4h`，`Sync`，`triggerSwitch: true`。UI 按钮文字不能代替后台状态。`$latest` 实际仍是 619 字节的纯日志诊断包，原本就不执行续费业务。

两个实验使用完全相同的诊断包，SHA256：

`4e89443a0c06b63452b89d8e895a8568a566f4ab87a4b66f8152ba2f3bfc0826`

| 版本 | 触发器 | 启用窗口 | 计划 | 自动日志 |
| --- | --- | --- | --- | --- |
| `$latest` | `renewal` | 12:35:11.023—12:38:32.177 | `@every 1m` / Sync | 未观察到 |
| 发布版本 `2` | `vp-timer-published-probe-20261019` | 12:38:37.402—12:41:58.089 | `@every 1m` / Sync | 未观察到 |

两组均观察三个周期，并定时停用。12:51:23 查询 12:34 之后的业务日志为空。12:52:28 和 12:52:29 分别手动调用两个版本，均 HTTP 200；随后业务日志能读到两次 `@@Start Request`、诊断标记和 `@@End Request`，没有 `SCHEDULED_TRIGGER`。诊断包对新手动标记显示 `UNLABELLED`，这些记录明确属于手动对照。

发布版本并未在本次有限观察窗口恢复自动调度，不能将根因直接归为 `$latest`。官方版本文档建议使用发布版本，未明确禁止 `$latest` 定时触发。

12:52:29 通过已登录控制台使用的接口，对已停用的版本 2 诊断触发器尝试保存 `cron(5 16 * * *)`，仍得到 HTTP 400：

```json
{"code":101212,"message":"schedule is invalid"}
```

读回确认失败没有改写计划，触发器仍停用。中国站目标是本地时间（Asia/Shanghai）每天 16:05；未用相对间隔 `@every 24h` 冒充固定时刻。

近 30 天项目监控：账号函数 7,780 次，定时器 10 次（含本次两个手动对照），平台成功率均 100%。配额查询接口未取得有效项目账单明细；当前手动调用成功，未发现调用次数耗尽证据，不能据此宣称已核验所有计费维度。
