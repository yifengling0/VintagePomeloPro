# 应用配置与游戏目录配置（1.4.8）

本轮在 `feature/account-cloud-membership-mvp` 实现配置保存与完整备份；应用维持 1.4.8 / 1004080，不做 AppGallery 发布。游戏存档仍不备份。

## 保存与恢复

- 普通游戏目录 `.pomelo/game.json` 保存稳定游戏身份、活动 EXE、分入口兼容设置与完整按键方案。目录移动、重新导入、卸载重装后可直接恢复；共享方案保持共享，主动编辑游戏专用方案时复制当前有效方案。
- 同时存在的游戏副本使用不同身份。目录缺失时保留轻量记录，不重建游戏目录；只读目录采用沙盒兜底，之后尝试写回。库扫描忽略 `.pomelo`，迁移时清理同目录旧卡片并转移收藏、排序及使用记录。
- 缺少目录配置文件时，不能仅凭通用引擎 EXE 的哈希认定为同一个游戏；只有 EXE、相对入口和游戏数据特征均一致、旧目录已缺失且候选唯一才恢复原配置。内容特征不足时不猜测匹配。
- Preferences 仍是现有消费者的配置接口。`UserConfigurationRepository` 通过明确注册表汇总全局设置、输入方案、游戏设置、排序/使用记录、系统壁纸字节和用户字体；模块沙盒 `filesDir/user_config` 保存清单、模块投影和资源。Wine 字体使用 ApplicationContext 的实际应用沙盒位置。
- 自动维护 Z 盘根 `.pomelo/app-settings-backup.zip` 的一份当前完整备份，写临时文件、完整校验后同盘替换。新安装先恢复这份本地包，再初始化配置消费者。
- 恢复使用持久 journal 和恢复前快照。中断启动时先回滚；恢复期间本地新修改记录到 journal 并保留。恢复后现有有效游戏目录配置优先，不能直接用云端覆盖它。
- 游戏封面和手动游戏背景保存在游戏目录，不上传图片。账号令牌、订单/权益、同步 journal、缓存、运行时、整个 Wine prefix、Steam 数据和游戏存档不在配置注册表中。

## 云协议与节流

完整快照为四个模块（settings / input_profiles / library / resources），输入方案沿用 schema 6。外层、游戏文件包含格式、最低读写版本及写入应用版本。无法理解的格式或必需功能保留原件并禁止反向覆盖。

配置协议：current → begin → missing chunks → upload → finalize。清单和成员分别校验 SHA-256；事务 CAS 仅在全部必需成员完整后发布 current head。256 KiB 分块，单快照上限 64 MiB。账号和 tablet / desktop 档案隔离。读取 current 本身不写事务；真正恢复时才建立 10 分钟 lease。旧对象和 job 元数据只在没有当前/活动引用后清理。

现有项目已验证 CloudDB，尚无 OBS 配置，所以首版使用配置专用 CloudDB 分块对象，每条 base64 数据小于 512 KiB。对象适配器可替换为 OBS，不改变客户端协议。游戏云存档通道继续关闭。

- 保存事件合并 700 ms；相同内容不重写游戏文件或 fallback 索引。
- 完整备份和旧版迁移通道成功后都停止定时任务。空闲状态不访问 session、capabilities、entitlement、head，也不提交同步 journal。
- 登录、返回前台和手动重新检查各检查一次；关闭自动备份后不做配置请求。会员失效、冲突或不可兼容配置等待状态改变或用户操作。
- 可重试错误按 60 / 120 / 240 / 300 秒退避。上传中新的本地修改只合并一个后续任务；失败不能把不完整版本标为成功。
- 服务器返回缺少的 chunk；未变图片/字体不上传。恢复时复用已校验的本地资源，并复用已读取的配置清单，避免重复下载。
- 切换账号不能自动上传上一账号的本地内容；旧同步 journal 的归属也在首次统一迁移时继承。
- 界面上的最近备份时间只取完整配置的成功记录；旧版单独方案同步的时间不会显示为完整备份完成。
